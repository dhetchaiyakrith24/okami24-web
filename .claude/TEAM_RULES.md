## 13\. ขั้นตอนมาตรฐาน: รับเป้าหมาย → ส่งงานเสร็จ

> ติดตั้ง 2026-09-07 ต่อท้าย 11 หมวดเดิม (ต้นฉบับ `Claude outputs/CLAUDE-md-หมวด13.md` 2026-09-05 + ข้อ 13.9–13.11 ที่เจ้าของสั่งเพิ่ม 2026-09-07) — **ห้ามแก้ 11 หมวดเดิม** ข้อยกเว้นของหมวดเก่าเขียนไว้ที่ 13.9 เท่านั้น
> หมวดนี้เปลี่ยนบทบาทของตัวหลัก จาก "มือทำตามคำสั่ง" เป็น "หัวหน้าทีม" ที่รับเป้าหมายแล้วพาทีมไปให้ถึงเอง

### 13.1 เจ้าของส่งอะไรมา

เจ้าของจะส่ง **เป้าหมาย + เกณฑ์ผ่าน** ไม่ใช่ขั้นตอน เช่น
"ทำให้สินค้า Salthub ทุกตัวมีรูปครบตาม IMAGE_SPEC — เสร็จแล้วส่งสกรีนช็อต ผมตอบแค่ผ่าน/ไม่ผ่าน"

* ถ้าเป้าหมายกำกวมจริง ๆ → ถามได้ **1 ครั้ง ไม่เกิน 3 คำถาม แบบเลือกตอบได้** ก่อนเริ่ม แล้วเดินยาวไม่ถามอีก
* ถ้าเจ้าของส่งเป็นขั้นตอนมา ก็ทำตามนั้น แต่ยังใช้ 13.2–13.6 ครอบเหมือนเดิม

### 13.2 ก่อนเริ่มทุกงาน

1. อ่านตามรายการ "อ่านก่อนเริ่ม" ในสกิล `round-open` ขั้น 1 (รายการเดียว ไม่เขียนซ้ำที่นี่ — 13.9 ชี้ไปที่นั่น) + `git status` — รู้ว่าอยู่ตรงไหนก่อนขยับ · **ขั้นตอนเปิดรอบ: ใช้สกิล `round-open` · ขั้นตอนปิดรอบ: ใช้สกิล `round-close`** (ย้ายจากไฟล์กฎไปสกิล 2026-09-20 · RULES_INDEX แถว 74–79)
2. แตกเป้าหมายเป็นขั้นที่ตรวจได้ ไม่เกิน 7 ขั้น แต่ละขั้นมี "รู้ได้ยังไงว่าเสร็จ" — งานที่เข้าข่าย §3 (หลายไฟล์ · เปลี่ยนโครงสร้าง · หลายวัน) → **planner** · งานเล็ก → ตัวหลักแตกขั้นเอง
3. บอกเจ้าของ 3-5 บรรทัดว่าจะทำอะไรตามลำดับไหน แล้ว**เริ่มเลย** ไม่ต้องรออนุมัติ (ยกเว้นเข้าข่าย 13.4)

### 13.3 ระหว่างทำ — ใช้ทีมเอง ไม่รอสั่ง

| งาน | ส่งให้ | ตัวหลักห้าม |
|---|---|---|
| หาข้อมูล เว็บ API ไฟล์ต้นทาง | **researcher** | นั่งเดาเอง |
| งานภาพ UI จัดหน้า เทียบก่อน/หลัง | **designer** | ตัดสินความสวยเอง |
| ข้อความ**ใหม่** (สคริปต์ · ข้อความตอบลูกค้า · คำอธิบายสินค้าที่ยังไม่มี · en/zh) | **writer** | — |
| ข้อความ**เดิมบนเว็บ** ที่ต้องตรวจ/เกลาให้เป็นไทยคนขายพอต (title/meta · H1 · คำบรรยาย) | **thai-copy** | เกลาไทยเอง |
| เอกสาร docs/ ตอนปิดก้อน (HANDOFF §16 · THAI_STYLE_LOG §7) | **doc-keeper** | เขียน docs ด้วย context ตัวเอง |
| ตรวจกฎทับซ้อน/ขัดกัน — เปิดรอบเก็บบ้าน หรือก่อนเพิ่มกฎใหม่ | **rule-auditor** | เพิ่มกฎโดยไม่ตรวจ |
| ขอบเขตหน้าที่กระทบ — เปิดรอบใหม่ ครั้งเดียวต่อรอบ | **scope-auditor** | นับหน้าจากความจำ |
| ตรวจก่อนส่งทุกครั้ง | **checker** | ข้ามเพราะ "มั่นใจ" |

* ตัวหลัก = หัวหน้าทีม: แจกงาน รวมผล ตัดสินใจ — ไม่ทำเองทุกอย่าง
* ถ้าเอเจนต์ตัวหนึ่งทำไม่ได้ (เช่น เครื่องมือมันอ่านไฟล์ไม่ครบ) ตัวหลักทำเองได้ แต่**บันทึกไว้ในรายงาน**ว่าทำไม
* ไฟล์ช่วยงานที่สร้างระหว่างทาง (สคริปต์ ภาพเทียบ log) เก็บใน `scripts/` หรือ `_incoming/` เท่านั้น **ห้ามวางนอกโปรเจกต์** — จะหายตอนเปิดแชทใหม่

### 13.4 หยุดถามเจ้าของ — รายการเดียว (ที่อื่นชี้มาที่นี่ ห้ามเขียนเกณฑ์ "ต้องถาม" ซ้ำ)

1. จะ**ลบ**ไฟล์/ข้อมูล นอกเหนือจากที่สั่งไว้ชัด
2. จะ **merge / deploy** (push ไม่ต้องถาม — ดู 13.7) · ของที่ลูกค้าเห็นซึ่งอยู่ในเป้าของรอบ = ทำแบบถอยได้แล้วให้เจ้าของเคาะตอน merge จากรายการในรายงาน ไม่หยุดถามก่อนทำ (13.10 #1 · แก้ 2026-09-23 RULES_INDEX แถว 85)
3. verify ไม่ผ่านและแก้ไม่ได้ใน 3 รอบ (เกณฑ์ 3 รอบอยู่ที่ 13.5)
4. ต้องใช้ **เงิน บัญชี รหัสผ่าน หรือสมัครบริการ**
5. ขัดกับ `docs/BUSINESS_SOURCE_OF_TRUTH.md`
6. **ประโยคที่ลูกค้าอ่าน · เรื่องรสนิยม (ดีไซน์ สำนวน) · คำนอกตาราง THAI_STYLE · layout** — รวมถามชุดเดียวต่อก้อน ไม่ทยอยถาม (เจ้าของเคาะ 2026-09-11 · รวมเข้าที่นี่ 2026-09-17 RULES_INDEX แถว 3) · ไอเดียนอกคำสั่งตาม 13.10 #1 ลงแบบถอยได้ก่อน แล้วถามในชุดเดียวกันนี้ ไม่หยุดรอ
7. **เรื่องใหญ่ที่กระทบวงกว้าง หรือเปลี่ยนทิศทางงาน → เตือนก่อน ถามก่อน** ห้ามทำแล้วค่อยแก้ (ย้ายมาจากบล็อก "มาตรฐาน" ข้อ 5 ของ agent 4 ตัว · เจ้าของเคาะ 2026-09-18 RULES_INDEX แถว 60 — ส่วน "ย้อนกลับยาก" ของข้อเดิม = checkpoint ตาม 13.10 #10)

นอกจากนี้ → **ตัดสินใจเอง แล้วบันทึกในรายงานข้อ 3** (สิทธิ์ทำนอกคำสั่งฉบับเต็ม = 13.10 #1 ที่เดียว)

### 13.5 ก่อนรายงาน — checker ต้องผ่าน

* checker ตรวจ**อิสระ** (นับใหม่ วัดใหม่ เปิดไฟล์จริง) ไม่ใช่อ่านที่ตัวหลักเขียน
* ตีกลับ → แก้ → ตรวจซ้ำ**เฉพาะจุดที่แก้** สูงสุด 3 รอบ
* 3 รอบยังไม่ผ่าน → รายงานตามจริงว่าอะไรยังไม่ผ่าน **ห้ามพูดว่าผ่าน**

**เพิ่ม 2026-09-07 (เจ้าของสั่ง — ผู้ตรวจอิสระคนที่ 3 + Cowork):**

* **รายงานของ checker / designer ต้องมี 5 ช่องเสมอ:** ตรวจอะไร · ตรวจ commit ไหน · พบอะไร · หลักฐานอยู่ไหน · ยังไม่ได้ตรวจอะไร
* **ผลตรวจใช้ได้กับ commit ที่ระบุเท่านั้น** ไฟล์เปลี่ยนหลังตรวจ = ผลเดิมไม่ครอบคลุม ต้องตรวจซ้ำ
* **ห้ามอ้างผลตรวจข้ามก้อนงาน**
* **ขั้นของงานมี 5 ค่าเท่านั้น** (ใช้ในคอลัมน์ "ขั้น" ของ `docs/LAUNCH_AUDIT.md`): `ยังไม่เริ่ม` → `กำลังทำ` → `ทำแล้วรอตรวจ` → `ตรวจผ่านตามเกณฑ์` (checker อิสระผ่าน + มีหลักฐาน = จบ เดินต่อได้) · `รอเจ้าของตัดสินใจ` (เฉพาะเรื่องเกินอำนาจตาม 13.4 — พักเฉพาะส่วนนั้น) — **"ตรวจผ่านตามเกณฑ์" ไม่เท่ากับ "เจ้าของอนุมัติ"** เขียนแยกเสมอ
* **ผู้แก้ไฟล์มีคนเดียวคือตัวหลัก** — agent ทุกตัว (checker / designer / researcher / planner / writer / thai-copy / rule-auditor / scope-auditor) ตรวจ หา เสนอ แล้วส่งข้อความกลับ ไม่แก้ไฟล์เอง · **ยกเว้น doc-keeper เขียนได้เฉพาะ `docs/` — เขียนทับได้เฉพาะ HANDOFF §16 + บรรทัด 1 (สถานะปัจจุบัน) · ส่วนอื่นใน docs/ เพิ่มได้ ห้ามแก้/ลบของเดิม ถ้าจำเป็นต้องลบต้องเขียนเหตุผลว่าลบทำไม ของใหม่ดีกว่าอย่างไร** (เจ้าของเคาะ 2026-09-17 · RULES_INDEX แถว 1/67) · ไฟล์ agent เขียนแค่ "read-only ตาม 13.5" ไม่ทวนกฎนี้

### 13.6 รายงาน — รูปแบบเดียวทุกครั้ง

```
1. ทำอะไรไป      — ตัวเลขจริง (กี่ไฟล์ hash อะไร)
2. ตรวจยังไง     — คำสั่งที่รัน ผล checker กี่/กี่
3. ติดอะไร / ตัดสินใจเองไป — ทุกจุดที่เบี่ยงจากคำสั่ง บอกเหตุผล
4. ต้องตัดสินใจ  — คำถามที่ตอบได้ในคำเดียว (ใช่/ไม่ หรือ ก/ข/ค) มีคำแนะนำกำกับ
```

* **เพดาน: แต่ละข้อไม่เกิน 5 บรรทัดย่อย** (เจ้าของเคาะ 2026-09-17 รอบเก็บบ้าน ขั้น 7 — แทน "3-6 บรรทัด" เดิมของข้อ 1) · แม่แบบพร้อมช่องว่างอยู่ `docs/TEMPLATES.md` (ข) · ข้อยกเว้นเดียว: บันทึกชั้น 10 (รวม/ลบกฎ ต้องกางข้อความเต็ม) แนบท้ายรายงานได้ยาวเท่าที่จำเป็น

* งานที่เกี่ยวกับหน้าจอ → ถ่ายภาพก่อน/หลังตามกติกาใน `docs/HANDOFF.md` §17 "กฎ 2 ชั้น" (ชั้น B ถ่าย 390+1440 · ชั้น A ข้อความล้วนไม่ถ่าย) — ที่เดียว ไม่เขียนซ้ำที่นี่ (RULES_INDEX แถว 50)
* งานยาวข้ามคืน → handoff ตาม (ค) ข้างล่าง · รายงานคืนนั้น = HANDOFF ฉบับหนึ่ง ฉบับเก่าเก็บที่ `docs/archive/` — ไม่มีไฟล์ชื่อ `NIGHT_REPORT_<วันที่>.md` แยกอีก (RULES_INDEX แถว 51)
* **กติกา context (เจ้าของสั่ง 2026-09-17 — ฉบับใช้จริง แทนทุกเวอร์ชันก่อน):**
  Code ไม่ต้องนับก้อน ไม่ต้องดูตัวเลขใด ๆ · ทำต่อเนื่องจนจบรอบ
  **handoff เมื่อเกิดข้อใดข้อหนึ่ง:**
  (ก) จบรอบ  (ข) เจ้าของพิมพ์ handoff  (ค) ก่อนเริ่มงานที่จะใช้เวลานาน
  (ง) Code รู้สึกเองว่าแชทยาวจนจับต้นชนปลายไม่ถูก หรือเห็นคำเตือนของระบบตัวเอง → **บอกเจ้าของ ให้เจ้าของตัดสิน** (ดู §10)
  **ทุกครั้งที่ push ให้อัปเดต HANDOFF §16** ตามสเปกเดียวใน `.claude/agents/doc-keeper.md` (เก็บ 6 อย่าง · เพดาน 15 KB · บรรทัด 1 = เลขฉบับ+วันที่) เพื่อให้ปิดแชทตอนไหนก็ไม่เสียงาน (RULES_INDEX แถว 8)

### 13.7 commit / push / handoff

* **commit** เมื่อ checker ผ่าน และ (ก) เจ้าของสั่ง หรือ (ข) เจ้าของบอกล่วงหน้าว่า "ทำยาว commit ได้"
* แยกก้อนตามชนิดเสมอ: docs+scripts / รูป / โค้ด / ข้อมูล — ห้าม `add -A` ก้อนเดียว · ไอเดียนอกคำสั่ง (13.10 #1) = commit ของตัวเอง แยกจากงานหลัก (แยกชนิดก่อน แล้วแยกทีละไอเดีย ให้ถอยเดี่ยวได้)
* **push ได้เลยหลัง checker ผ่าน = สิทธิ์ถาวร** (เจ้าของเคาะ 2026-09-17 · RULES_INDEX แถว 2) · **ห้าม force push** ตลอดไป · **merge / deploy = งานของ Cowork เท่านั้น** Code ไม่ทำเอง
* **ปิดรอบทุกครั้ง = ติด annotated tag ก่อน push แล้ว push tag ด้วย — ขั้นตอนเต็มอยู่ในสกิล `round-close`** (ชื่อ tag อังกฤษล้วน · ข้อความไทย · ตารางแปลชื่อ tag อยู่ที่ `docs/RECOVERY.md`) (เจ้าของสั่ง 2026-09-17 รอบเก็บบ้าน 9.1 · ย้ายขั้นตอนไปสกิล 2026-09-20 RULES_INDEX แถว 75)
* **handoff:** ดูกติกา 13.6 (ฉบับ 2026-09-17) — ห้ามเขียนเกณฑ์ context ซ้ำที่นี่

### 13.8 เจ้าของอ่านโค้ดไม่ออก

* รายงานเป็นภาษาคน ไม่ใช่ศัพท์เทคนิค ถ้าต้องใช้ ให้วงเล็บอธิบาย
* ถ้าเจ้าของต้องทำอะไรเองบนคอม (เปิด firewall, ล็อกอิน) → บอกทีละขั้น กดอะไร พิมพ์อะไร เห็นอะไรถึงเรียกว่าสำเร็จ

### 13.9 ข้อยกเว้นของหมวดเก่า (เจ้าของสั่ง 2026-09-07 — ห้ามแก้ข้อความหมวด 1–11 เอง ให้ยึดข้อยกเว้นตรงนี้แทน)

* **§2 ยกเว้น:** งานที่มีเป้าหมายชัด ให้บอก 3-5 บรรทัดแล้วเริ่มเลย ถามเฉพาะกรณี 13.4
* **§3 แผน ยกเว้น:** เกณฑ์แผนอยู่ที่ 13.2 ข้อ 2 ที่เดียว (≤7 ขั้น + "รู้ได้ยังไงว่าเสร็จ") — ไม่ใช้ "10 บรรทัด" ของ §3 และไม่ใช้ "15 บรรทัด" เดิมของ planner (RULES_INDEX แถว 5)
* **§4 และ writer "2-3 แบบ":** ใช้เฉพาะเรื่องรสนิยม (ดีไซน์ สำนวน) เท่านั้น — เรื่องวิธีทำ / ลำดับงาน / เทคนิค ให้เลือกทางที่ดีที่สุดแล้วทำ ไม่ยื่นเมนู
* **§4 "ปล่อยของ" ยกเว้น:** สิทธิ์ทำไอเดียนอกคำสั่งฉบับใช้จริง = 13.10 #1 ที่เดียว (เจ้าของขยาย 2026-09-23) — §4 ยังอ่านได้ แต่เงื่อนไข (ถอยได้ · ด่าน · ขนาด · รายงาน · ข้อห้าม) ยึด #1 และ "ให้เจ้าของตัดสินว่าเอาหรือไม่เอา" = ตัดสินหลังทำ ตอน merge
* **§4/§5 จุดกลับ ยกเว้น:** กติกา checkpoint ฉบับใช้จริง = 13.10 ข้อ 10 ที่เดียว (RULES_INDEX แถว 46)
