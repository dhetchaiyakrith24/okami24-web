## 13. รับเป้าหมาย → ส่งงานเสร็จ (ตัวหลัก = หัวหน้าทีม ไม่ใช่มือทำตามสั่ง)

### 13.1 รับงานและเริ่ม

1. เจ้าของส่งเป้าหมาย (กฎกลาง §12 ข้อ 2) · ส่งเป็นขั้นหรือสั่งวิธีมา = อ่านเป็นเป้า (13.8)
2. เปิดรอบ = สกิล `round-open` · ปิดรอบ = สกิล `round-close` · handoff = สกิล `okami24-handoff` (ไม่ใช่ `anthropic-skills:handoff` ของบัญชี)
3. งานใหญ่ตามกฎกลาง §12 ข้อ 12 (ในเว็บ = กระทบหลายไฟล์ · เปลี่ยนโครง · เปลี่ยนหน้าตาเว็บอย่างมีนัยสำคัญ · หรือหลายวัน) → วางแผนก่อน
   · ซอยแผนให้เห็นผลใน 7–14 วัน · เกิน 14 วัน = เตือนเจ้าของในข้อความของ #4 แล้วเริ่ม ไม่รอ · งานเล็กแตกขั้นเอง
4. บอกเจ้าของ 3–5 บรรทัดว่าจะทำอะไรตามลำดับไหน แล้ว**เริ่มเลย** — หยุดรอเฉพาะเข้าข่าย 13.3

### 13.2 ทีม (คำแนะนำ ไม่ใช่ขั้นบังคับ · ตัวหลักทำเองเมื่อเร็วกว่าและได้ผลเท่ากัน · เงื่อนไขเรียกเต็ม = บรรทัด `description` ในไฟล์ agent)

| งาน | ถนัด |
|---|---|
| หาข้อมูลจากแหล่งจริง · คู่แข่ง ตลาด ราคาตลาด สินค้าขายดี | `researcher` |
| หน้าตา ช่อง หรือคอมโพเนนต์ใหม่ (13.5 #6) | `designer` |
| ข้อความบนเว็บ 3 ภาษา — เขียนใหม่หรือเกลา (น้ำเสียง = THAI_STYLE §2 "น้ำเสียง") | `thai-copy` |
| กฎทับซ้อน/ขัดกัน (เก็บบ้าน · เปลี่ยนกฎหลายข้อพร้อมกัน) | `rule-auditor` |
| ขอบเขต — รอบที่แตะส่วนที่ทุกหน้าใช้ร่วม หรือเกิน 3 หน้า | `scope-auditor` |
| SEO: head / JSON-LD / คำค้นแย่งกัน (รอบ SEO · วันวัดผลใน SEO_BASELINE) | `seo-auditor` |
| ตามงานค้าง — งานประจำทุกวัน 13:00 `okami24-follow-up-morning` + บรรทัดเตือนตอนเปิดแชท (`scripts/stale-work.js`) | `follow-up` |
| ลูกค้าจำลองเดินเว็บทดสอบ — งานใหญ่ · หน้าตาใหม่ · ปิดรอบที่ลูกค้าเห็นของเปลี่ยน · ก่อนเปิดของสำคัญ · บรีฟ = ที่อยู่เว็บทดสอบ + เป้าของลูกค้าเท่านั้น | `visitor` |
| **ตรวจก่อน merge — บังคับตัวเดียว** (ทุก PR ยกเว้นกรณีที่ 13.4 ให้เขียน `Checker: SKIP`) | `checker` |

* **agent หรือสกิลตัวใหม่ = เสนอเจ้าของก่อน** (กฎกลาง §12 ข้อ 28) · ตัวที่ไม่มีใครใช้แล้ว = Friday ลบเองได้แล้วบอกในรายงาน (13.3 #1)
* ผู้แก้ไฟล์มีคนเดียวคือตัวหลัก — agent ทุกตัวตรวจ หา เสนอ แล้วส่งข้อความกลับ · agent ทำงานไม่ได้ = ตัวหลักทำเอง แล้วบอกเหตุผลในรายงาน
* ไฟล์ช่วยงานอยู่ใน `scripts/` หรือ `_incoming/<รอบ>/` เท่านั้น · `_incoming/` ไม่เข้า git → รอบคลาวด์ (หรือเมื่อ Javis/แชทคลาวด์ต้องใช้ต่อ) สรุปลง `docs/cloud-results/<รอบ>.md`
* **สกิลเขียนอะไรได้:** ห้ามตัวเลขที่คาดว่าจะได้ (จำนวนหน้า สินค้า ผลตรวจ) และชื่อไฟล์ใน `src/` (ชี้ที่มาแทน — รายชื่อไฟล์ `src/` ที่สกิลใช้ = HANDOFF §17)
  · agent ที่ต้องอ่าน `src/` เขียนชื่อไฟล์ได้เป็น path เต็มใน backtick · ได้ = ชื่อสคริปต์ใน `scripts/` · เลขข้อกฎ · วันที่/ชื่อรอบที่กำกับที่มา

### 13.3 หยุดถามเจ้าของ — รายการเดียว (ที่อื่นชี้มาที่นี่ ห้ามเขียนเกณฑ์ "ต้องถาม" ซ้ำ)

1. จะ**ลบของที่ git กู้คืนไม่ได้** (ไฟล์นอก git · ฐานข้อมูล · ของบนบริการภายนอก) หรือของที่ยังใช้งาน/ยังค้างทำอยู่ — ของใน git ที่ล้าหลัง
   ยกเลิกแล้ว หรือไม่มีใครอ้างถึง = ลบได้แล้วบอกในรายงาน (แทนกฎกลาง §8 บรรทัด "ห้ามลบไฟล์สำคัญหรือลบทีละหลายไฟล์โดยไม่ถาม")
   · **branch ที่ merge เข้า main แล้ว ทั้งในเครื่องและบน GitHub = ลบเองได้** (แทนกฎกลาง §8 บรรทัดเดียวกัน) — ข้อยกเว้นและวิธี = สกิล `house-clean` "รายการเดียว" ข้อ 1
2. ต้องใช้ **เงิน บัญชี รหัสผ่าน หรือสมัครบริการ** — ยกเว้นขยับเครื่อง Render ขึ้นชั่วคราวตอน build แรมไม่พอ แล้วลดกลับทันที (`docs/DEPLOY-RENDER.md` · ทำแล้วบอกเจ้าของทุกครั้ง ·
   แทนกฎกลาง §12 ข้อ 13 ท่อน "เงินหรือบัญชี" และข้อ 14 ท่อน "เงิน … รอคำตอบเสมอ" — เฉพาะเรื่องนี้)
3. ขัดกับ `docs/BUSINESS_SOURCE_OF_TRUTH.md`
4. **เปลี่ยนทิศงาน · ต้องแตะ【ห้ามแตะ】ของรอบ (หรือรายการ HANDOFF §17 "Do not touch" ที่ไฟล์คำสั่งรอบไม่ได้ระบุให้แตะ) · หรือถอยด้วย revert ครั้งเดียวไม่ได้** → เตือนก่อน ถามก่อน ห้ามทำแล้วค่อยแก้
5. จะแตะของที่เจ้าของพอใจหรืออนุมัติแล้ว → บอกก่อน รอคำตอบเฉพาะส่วนนั้น ส่วนอื่นทำต่อ (กฎกลาง §12 ข้อ 21)
6. **push / merge ไม่ผ่าน** → หยุดข้อนั้น บอก error ตรงตัว ห้ามหาทางอ้อม
7. verify ไม่ผ่านและแก้ไม่ได้ใน 3 รอบ → รายงานตามจริง ห้ามพูดว่าผ่าน
8. **คำสั่ง คำตอบ หรือคำที่อ่านได้มากกว่า 1 แบบ** แล้วผลต่างกัน → ห้ามเดา บอกว่าอ่านได้กี่แบบ ให้เลือกเป็นตัวเลือกพร้อมคำแนะนำ
   ส่วนที่ไม่ติดทำต่อ (กฎกลาง §12 ข้อ 13 — ต้องอยู่ในรายการนี้)
9. เรื่องที่**กฎกลาง §8–§9 สั่งให้ถาม** (ระบบล็อกอิน · ฐานข้อมูล · ระบบจ่ายเงิน · env · ตั้งค่า Windows · โหลด/รันไฟล์ที่ไม่รู้ที่มา)
   · ไฟล์ที่ตัวล็อกเด้งถามเพราะไฟล์คำสั่งรอบไม่มีบรรทัด【แตะได้】(13.7)

**ถามแล้วเจ้าของยังไม่ตอบ** (กฎกลาง §12 ข้อ 14 · เวลารอ 30 / 5 นาทีอยู่ที่นั่น):
* **รอคำตอบเสมอ** = #1 · #2 (เว้นข้อยกเว้น Render ในข้อ 2) · #9 · #4 ท่อน "ถอยด้วย revert ครั้งเดียวไม่ได้" · PR สต็อกที่ผิดปกติ และเปิดขายกลับด้วย `--reopen` (13.7) ·
  **ส่งถึงคนนอก** (กฎกลาง §12 ข้อ 14: "ข้อความถึงลูกค้า คู่ค้า ดีลเลอร์ · โพสต์ · เปิดให้คนนอกเห็นครั้งแรก") แม้ติด #5 หรือ #8 —
  ในเว็บนี้ "เปิดให้คนนอกเห็นครั้งแรก" ไม่รวมการลงสินค้าหรือหน้าใหม่บนเว็บที่เปิดอยู่แล้ว · ระหว่างรอทำส่วนอื่น
* **ครบ 30 นาทีแล้วเลือกทางที่แนะนำเอง** = #3 · #4 ท่อนเปลี่ยนทิศ / 【ห้ามแตะ】 · #5 · #8 → ลงมือแบบถอยได้ แล้วเขียนในรายงานว่าเลือกเองเพราะยังไม่ได้คำตอบ ·
  #3 = ทางที่เลือกต้องไม่ขัด BSOT และไม่แก้ BSOT (ทำส่วนที่ไม่ขัด · เรื่องที่ขัดยังรอ)
  (แทนกฎกลาง §12 ข้อ 13 ท่อน "อ่านได้มากกว่า 1 แบบ = ห้ามเดา … ให้เลือกก่อนทำ" และข้อ 21 ท่อน "รอคำตอบเฉพาะส่วนนั้น" — เฉพาะเมื่อถามแล้วครบ 30 นาทีไม่มีคำตอบ)
* #6 #7 ไม่ใช่คำถาม (รายงานตามจริง) · คำถามนอกรายการ = ถามได้ ไม่หยุดรอ ทำส่วนอื่นต่อ
* จับเวลา = ตอนส่งคำถาม เปิดคำสั่งรอเบื้องหลัง (Bash `run_in_background` · `sleep 1800` หรือ `sleep 300`) มันปลุกเมื่อครบ — ไม่นับเวลาจากความจำ

**นอกรายการนี้ไม่หยุดถาม** — ประโยคที่ลูกค้าอ่าน · รสนิยม (ดีไซน์ สำนวน layout) · คำนอกตาราง THAI_STYLE = เลือกเองแบบถอยได้
แล้วยกขึ้นหัวข้อ "ต้องตัดสินใจ/ทำ" ของรายงาน รวมชุดเดียว (13.8 · กฎกลาง §12 ข้อ 15) · ที่เหลือ → **ตัดสินใจเอง แล้วเขียนในข้อ "ตัดสินใจเอง" ของรายงาน**
* สกิล agent และเอกสารอื่นห้ามเพิ่มจุด "ต้องถาม/รอเจ้าของ" — ชี้มาที่ 13.3 · จุดรอเจ้าของนอกรายการนี้ = PR สต็อกที่ติดเงื่อนไขผิดปกติ · เปิดขายกลับจากการอ่านหน้ารายการสินค้า (`--reopen`) (ทั้งคู่ 13.7) ·
  ภาพเทียบรูปสินค้าใหม่ก่อน merge (13.5 "รูปสินค้าใหม่" · รอเสมอ ไม่นับ 30 นาที) ·
  งานเต็มของหน้าตาใหม่ที่ไม่มีของเดิมให้เทียบและยังไม่มีรูปอ้างอิง = รอรูปเสมอ ไม่นับ 30 นาที (กฎกลาง §6 — ระหว่างรอทำร่างและส่วนอื่นต่อ)
* **คำถามถึงเจ้าของ = เรื่องที่เจ้าของตัดสินได้** (ธุรกิจ · รสนิยม · ทิศงาน) · ทางเลือกเทคนิคล้วน (ตัวล็อก สคริปต์ วิธีตรวจ) = Friday เลือกเองแล้วรายงาน
  รวมกฎ/คู่มือที่ขัดกันเรื่องเทคนิคล้วน (กฎกลาง §12 ข้อ 15 · แทนกฎกลาง §12 ข้อ 28 ท่อน "ของซ้ำที่ขัดกัน … ส่งตารางให้เจ้าของเคาะ" เฉพาะเรื่องเทคนิค)
* **คำถามหลายเรื่อง = ชุดเดียว** ทุกข้อมีตัวเลือกและคำแนะนำ เจ้าของตอบ "ตามแนะนำ" คำเดียวได้ทั้งชุด
* **เจ้าของตอบ "ไม่เข้าใจ" 2 ครั้งในเรื่องเดียว** = Friday ตัดสินแบบถอยได้ ไม่ถามรอบ 3 แล้วเขียนในข้อ "ตัดสินใจเอง" ของรายงาน

### 13.4 ตรวจ — checker ผ่านก่อน merge

* **ก่อนส่ง checker ทุก PR = `node scripts/pre-checker-gate.js` ขึ้น `GATE PASS`** (รายการด่าน = หัวสคริปต์) · ตก = แก้แล้วรันใหม่ ไม่ใช่จุดถามเจ้าของ
  (ยกเว้นแถว `locked` = 13.3 #9) · ผ่านแล้วตัวล็อกตรึง tree นั้นและเครื่องทดสอบ (หัว `scripts/guard-tool.js` H · H+) จนกว่ารายงานกลับแล้วรัน `--done`
  (โน้ตหมดผลเองใน 3 ชม. · checker ทำนานกว่านั้น = รันด่านใหม่)
* checker ตรวจ**อิสระ** (นับใหม่ วัดใหม่ เปิดไฟล์จริง) · รายงานของ checker/designer = 5 ช่อง (สเปกในไฟล์ agent)
* **ผลตรวจใช้ได้กับ commit ที่ระบุเท่านั้น** — ไฟล์เปลี่ยนหลังตรวจ = ตรวจซ้ำเฉพาะจุดที่แก้ (ข้อยกเว้นเดียว = 13.5 #2 (จ)) · ห้ามอ้างผลตรวจข้ามก้อน
* ตีกลับ → แก้ → ตรวจซ้ำ สูงสุด 3 รอบ · ไม่ผ่าน = 13.3 #7
* **ผล checker อยู่ในคำอธิบาย PR** — `Checker: PASS <sha>` (sha ของ commit หัวที่ตรวจ ≥ 7 ตัว) · PR ที่ไม่ต้องส่ง checker = `Checker: SKIP <เหตุผล>`:
  เอกสารล้วนหรือหลังบ้านตรวจเอง (13.7) · แก้หลังผ่านตาม 13.5 #2 (จ) · PR ระหว่างงานชุดยาว 13.5 #1 · ไม่มีบรรทัด หรือ PASS แต่ sha ไม่ตรงหัว PR = `self-merge-check --pr` ตอบ `BLOCKED`

### 13.5 ตรวจแค่ไหน — ที่เดียว (ถอยได้ง่าย = ตรวจเท่าที่จำเป็น · กฎกลาง §12 ข้อ 23)

**ชั้นของงาน:** ชั้น A = ข้อความล้วน → ไม่ถ่ายภาพ · ชั้น B = แตะโครงหรือหน้าจอ (ไม่แน่ใจ = ชั้น B) → ก่อน merge ต้องมีภาพก่อน/หลังจุดที่เปลี่ยน
390 + 1440 จากเครื่องชนิดเดียวกัน (สกิล `tier-b-proof`) + checker · merge แล้วส่งภาพให้เจ้าของในรายงาน
* **ตอนเปิดดูภาพ (Friday และ checker) ใช้รายการ "Owner eye" ใน `designer.md`** — ไม่รอเจ้าของ
* **ก่อน/หลัง วัดบนเครื่องทดสอบ** (build ของ main = ก่อน) ไม่ดึงจากเว็บจริง (bandwidth ของ Render) · เว็บจริง = curl หน้าที่แตะหลัง merge เท่านั้น
  · **เครื่องทดสอบต้องเหมือนเว็บจริง:** เปิดตะกร้า (`scripts/test-server.js build` เปิดให้เอง) · แตะหัวเว็บหรือส่วนที่ข้อความเปลี่ยนตามการล็อกอิน = วัดทั้งล็อกอินและไม่ล็อกอิน
  · ตั้งใจอ่านเว็บจริงด้วยเครื่องมือสแกน/ถ่ายภาพ = `OKAMI24_LIVE_OK=1` นำหน้า แล้วบอกเหตุผลในรายงาน
* **งานภาพในเว็บ "เสร็จ" = merge ขึ้นเว็บ + ส่งภาพในรายงานแล้ว** · รายงานเขียนแยกว่าเจ้าของยังไม่ได้เคาะ · เจ้าของเคาะเก็บหรือถอยหลัง merge
  (แทนกฎกลาง §6 บรรทัด "งานภาพไม่ถือว่าเสร็จ จนกว่าเจ้าของจะได้เห็นของจริงแล้วบอกว่าโอเค")
* **รูปสินค้าใหม่:** checker ผ่าน → ส่งภาพเทียบต้นแบบ (รูปผู้ผลิต / ร้านอื่น) กับรูปใหม่ ทุกรูป ให้เจ้าของในแชท → **merge เมื่อเจ้าของตอบผ่าน**
  (วิธีและภาพเทียบ = `docs/IMAGE_SPEC.md` §0 ข้อ 7 + §7 · ถอยกลับไปรูปเดิม · รูปรวมที่สคริปต์ต่อจากรูปที่ผ่านแล้ว = ไม่ต้องส่ง) · ไม่ส่งร่างระหว่างทำ (แทนกฎกลาง §12 ข้อ 22 ท่อนส่งร่างให้ดูบ่อยก่อนทำเต็ม — เฉพาะรูปสินค้า · หน้าตาใหม่ยังส่งร่างตามกฎกลาง)

1. **ทางด่วน** — แก้ข้อความ/ข้อมูล 1–3 หน้า ไม่แตะหน้าตา ไม่แตะรายการชุดเต็ม (#3): ด่านคำของสกิล `thai-check` + `scripts/scan.js` → checker
   รอบเดียวบรีฟแคบ → ด่าน GitHub เขียว → merge → curl หน้าจริง · **งานชุดยาวแบบที่เจ้าของผ่านแล้ว** (เช่น ทีละแบรนด์) = checker ครั้งเดียวตอนจบชุด
   (PR ระหว่างชุด = `Checker: SKIP series n/N (13.5 #1)` · PR สุดท้าย = `PASS`) ด่าน GitHub ทุก PR
2. **ชุดเบา = ค่าเริ่มต้น** ของงานที่ถอยได้ด้วย revert ครั้งเดียว:
   (ก) tsc + eslint ไฟล์ที่แตะ + **PR ที่แตะเว็บ = `npx tsx scripts/verify-catalog.ts --full` บน worktree ทดสอบของ PR ที่ commit หัว** (ห้ามรันในโฟลเดอร์หลัก ·
       `pre-checker-gate` ด่าน `full` ตกถ้าไม่มี) ·
   (ข) ข้อความที่ลูกค้าเห็นเปลี่ยน = ด่านของสกิล `thai-check` บนหน้าที่แตะ + หน้าที่ข้อความนั้นขึ้น (ทั้ง sitemap ตาม #5) ·
   (ค) ชั้น B = `scripts/visible-text.js` ก่อน/หลัง หน้าที่แตะ + หน้าที่การ์ดหรือข้อความของหน้านั้นขึ้นด้วย (หน้าแบรนด์ หมวด `/products` หน้าแรก) + หน้าควบคุม 2–3 หน้า ·
   (ง) ข้อความไทยบนหน้าเปลี่ยน = `scripts/wordbreak-scan.js` ·
   (จ) checker 1 ครั้งต่อก้อน · **แก้หลัง checker ผ่าน = ไม่ส่งซ้ำ ให้ด่าน GitHub ตัดสิน** เมื่อครบทุกข้อ:
       – ไม่แตะไฟล์ข้อ (1) ของ 13.7 · อยู่ใน PR ที่ด่าน GitHub รันจริง
       – ข้อความที่ลูกค้าเห็นเปลี่ยน = แค่เกลาคำ (ไม่เพิ่มข้อเท็จจริงหรือตัวเลข) + ตัวหลักอ่านหลังแก้ที่ 390 + 1440 + ด่านคำ (ข) ผ่าน
       – คำอธิบาย PR มีบรรทัด `Checker: SKIP after-pass (13.5 #2 (จ))` ·
   (ฉ) หลัง merge curl หน้าที่แตะบนเว็บจริง · title/meta/H1 อาจขยับ = `scripts/head-audit.js` ทั้งเว็บบนเครื่องทดสอบ ก่อน/หลัง
3. **ชุดเต็ม:** เงิน/ตะกร้า/การสั่งซื้อ · ข้อมูลลูกค้า · แตะรายการข้อความห้ามเอง (THAI_STYLE §3 + HANDOFF §17 "Do not touch") · ไฟล์ข้อ (1) ของ 13.7 ·
   งานที่ถอยยาก · ไม่แน่ใจ — ชุดเต็ม = ขั้นของสกิล `round-close` + `tier-b-proof` ครบ
   · **งานหลังบ้าน = ชุดเบา** ยกเว้นไฟล์ข้อ (1) ของ 13.7 (หน้า `/staff` · สคริปต์ · เอกสาร): แม้แตะโค้ดออเดอร์ ตราบใดที่ไม่เปลี่ยนสิ่งที่ลูกค้าเห็น
     ยอดเงิน หรือข้อมูลลูกค้าที่เก็บ · ภาพก่อน/หลังเฉพาะจุดที่เปลี่ยน ที่ 390 · ใครตรวจ = 13.7

### 13.6 รายงาน · context · handoff

* **รายงาน = กฎกลาง §12 ข้อ 10** — ของเว็บที่ใส่เพิ่ม (แม่แบบ `docs/TEMPLATES.md` (ข)): หน้าเว็บเปลี่ยน = ลิงก์เว็บจริงของทุกหน้าที่แก้ + ชื่อสินค้าที่ลูกค้าเห็น ·
  ของเทคนิค (hash · context · คำสั่ง · ที่อยู่ไฟล์หลักฐาน) ไม่อยู่ในรายงาน — อยู่ในคำอธิบาย PR หรือไฟล์หลักฐานที่ลิงก์จากข้อ "ทำอะไร"
* **หน้าสรุปงานของเจ้าของ** (กฎกลาง §12 ข้อ 4 · ที่อยู่ วิธีอัปเดต และหัวข้อ = HANDOFF §17 "Owner status page"): **อัปเดตทุกครั้งที่งานหนึ่งชิ้นจบ**
  (merge · ปิดรอบ · แชทลูกจบ) · ภาษาเจ้าของ ไม่มีชื่อไฟล์/เลข PR · ผู้เขียน = Friday + งานตามงาน 13:00 (เฉพาะหัวข้อ "ค้างนาน") · อ่านหน้าล่าสุดก่อน publish ทุกครั้ง ·
  แชทลูกไม่แก้หน้านี้เอง — รายงานกลับแล้ว Friday อัปเดต
* **คำตัดสินชั่วคราว** = จดพร้อม **วันหมด** เสมอ · ปิดรอบ = เช็คว่ามีค้างไหม แล้วลบ (สกิล `round-close` ขั้น 6)
* **context และโควตา (เครื่องมือของกฎกลาง §12 ข้อ 29):** `mcp__ccd_session_mgmt__get_usage` **ก่อนเริ่มงานยาว และก่อนเขียนรายงานหลัง merge หรือปิดก้อน** ·
  โควตาแผน (ช่อง `plan`) เกิน 80% = บอกเจ้าของ · agent = เรียกตามที่งานต้องใช้ · คลาวด์ไม่มีเครื่องมือนี้ = ข้อ 29 "วัดไม่ได้" บอกตรง ๆ

* **handoff = สกิล `okami24-handoff`** (เมื่อไหร่ · สเปก §16) · ตัวหลักเขียน §16 เองทุกครั้ง **เขียนทับ ไม่ย้ายข้อความเก่าไปเก็บ**
* **ย้ายแชทในเว็บ:** commit + push ทุกอย่างลง branch งาน ทั้งที่ตรวจแล้วและยังไม่ตรวจ · §16 บอกว่า commit ไหนยังไม่ผ่าน checker ·

* **งานตั้งเวลาที่ไม่มีคนเฝ้า** = โหมดของงานเป็น Auto ในแอป (แก้งาน → โหมด) · คำสั่งอ่านอย่างเดียวอนุญาตไว้ใน `.claude/settings.json` ·
  คำสั่งละครั้ง ไม่ต่อ `cd … &&` — ไม่งั้นค้างรอกดอนุญาตทั้งคืน
* **งานเบื้องหลัง** (build · สแกน · เครื่องทดสอบ · ตัวรอ) = มีเวลาตัดจบทุกตัว เกินแล้วหยุดและแจ้ง · ตัวหลักกลับมาดูทุก ≤ 10 นาที
  (ตั้งตัวปลุกเบื้องหลัง) · ห้ามปล่อยงานรอเงียบ · ตัวจับเวลารอคำตอบของ 13.3 ไม่นับ

### 13.7 commit / push / merge / deploy

* **commit + push ลง branch งานได้ทุกเมื่อ** รวมงานที่ยังไม่ตรวจ · ยังไม่ตรวจ = ยังไม่ผ่าน และไม่ใช่จุดถอย
  · **PR = draft จนกว่า checker ผ่าน** (`gh pr create --draft` · ด่าน `pre-checker-gate` และ checker ทำบน draft ได้) · ผ่านแล้ว `gh pr ready` **ครั้งเดียว** ให้ด่าน GitHub รัน แล้ว merge · ตีกลับ = `gh pr ready --undo` ก่อนแก้
    (push เข้า PR ที่ไม่ใช่ draft = ด่าน GitHub กินนาที Actions ที่เสียเงิน)
* แบ่ง commit ให้ถอยทีละเรื่องได้ · add ไฟล์ทีละชื่อหลังดู `git status --short` · ไอเดียนอกคำสั่งที่ลูกค้าเห็น = commit ของตัวเอง
* **PR ละ 1–3 สินค้าของแบรนด์เดียวกันได้** — commit แยกต่อสินค้า · build ด่านตรวจ และ checker ครั้งละชุดต่อ PR · หลัง merge พังบางหน้า = แก้เฉพาะจุดด้วย PR ใหม่
* **รวมงานเล็กเป็นก้อน ขึ้นเว็บครั้งเดียว:** งานเล็กที่พร้อมใกล้กัน = PR เดียว commit แยกต่อเรื่อง — ทุก deploy = เว็บดับสั้น ๆ (HANDOFF §17 "Render after a merge")
  + build + checker หนึ่งรอบ · ของพังหรือราคาผิด = ไม่รอรวม
* **ตัวล็อก** (รายการเต็ม = หัว `scripts/guard-tool.js` · `scripts/push-guard.js` · `.githooks/` · Chrome ทีละงาน `scripts/lib/chrome.js` — ทุกตัวมีตัวอย่างปลอมใน
  `node scripts/pre-checker-gate.js --self-test` ที่ house-check รันทุกสัปดาห์): ห้าม force push · ห้าม push ขึ้น main ตรง · ห้ามปิด node ทั้งเครื่อง ·
  เขียน `render.yaml` / `.env*` / `ordering-mode.ts` / `thai-typography.ts` (THAI_STYLE §5) = ไฟล์คำสั่งรอบต้องมีบรรทัด【แตะได้】ชื่อไฟล์นั้น
  ไม่มี = เด้งถามเจ้าของ · ตัวล็อก git ต้องเปิดอยู่ (`core.hooksPath` = `.githooks`) · ไฟล์ใหญ่ วิดีโอ เสียง ไม่เข้า git · ตัวล็อกปัด = ทำตาม ไม่หาทางเลี่ยง
* **merge — Friday merge ทุก PR ของรีโปนี้เอง** (บนคอมและคลาวด์ · Javis merge เฉพาะเมื่อเจ้าของสั่ง) · **ไม่หยุดถามก่อน merge** — merge แล้วรายงาน
  · ก่อน merge ทุก PR: บรรทัด `Checker:` (13.4) + ด่าน GitHub เขียวทุกตัว (ข้ามเพราะไม่แตะเว็บ = นับว่าผ่าน · แดงหรือยังรัน = ยังไม่ผ่าน ·
    deploy ถูกข้ามตอนเป็น draft = `gh pr ready --undo` แล้ว `gh pr ready`)
  · **ไม่ต้องส่ง checker — Friday อ่าน diff เองแล้ว merge:** **PR เอกสารล้วน** (ทุกไฟล์อยู่ใน `docs/` · `.claude/LESSONS.md` · `.claude/LESSONS-images.md` · `.claude/memory/`)
    และ **PR หลังบ้านที่ไม่แตะตัวล็อก เงิน หรือข้อมูลลูกค้า** — ทั้งคู่ต้องให้ `self-merge-check` ขึ้น `SMALL` · self-review ไม่ครอบ กฎ/สกิล/agent · ตัวด่าน · สต็อก ออเดอร์ เงิน ลูกค้า
    (`self-merge-check --pr` ปัดเอง) · คำอธิบาย PR = `Checker: SKIP docs-only (13.7)` หรือ
    `Checker: SKIP self-review (13.7)` · checker สุ่มตรวจ PR self-review ที่ merge แล้วสัปดาห์ละครั้ง (สกิล `house-clean` (ก)) · เจอของพัง = แก้เป็น PR ใหม่
  · **PR สต็อกรายชั่วโมง** = Friday merge เองได้ ไม่รอเจ้าของ · **ผิดปกติ** (เกณฑ์ = HANDOFF §17 "Stock PR anomaly") = ค้างเป็น draft แล้วถามเจ้าของ ·
    อ่านจากหน้าคีย์ออเดอร์ = ปิดและเปิดขายกลับได้เอง · อ่านจากหน้ารายการสินค้าอย่างเดียว = ปิดได้อย่างเดียว เปิดกลับรอเจ้าของยืนยันแล้ว Friday ใช้ `--reopen`
  · PR ใหญ่ = รายงานแยกบรรทัด (เปลี่ยนอะไร · ถอยยังไง — ภาษาเจ้าของ เลข PR อยู่ในคำอธิบาย PR ตามกฎกลาง §12 ข้อ 10) · ชั้น B = ส่งภาพก่อน/หลัง 390 + 1440 ในรายงาน ถอยด้วย revert
  · งานรูปสินค้า = `docs/IMAGE_SPEC.md` §7 (รูปแบบใหม่/ต้นแบบไม่ชัด = หัวข้อ "ต้องตัดสินใจ/ทำ" ของรายงาน)
* **ใหญ่ = ข้อใดข้อหนึ่ง:** (1) ตัวที่ทำงานเองหรือตัดสิน merge/deploy (settings · hook และสคริปต์ที่ hook เรียก · `.github/` · สำเนากฎกลาง ·
  `launch.json` · ตัวด่าน) (2) เงิน ออเดอร์ สต็อก ข้อมูลสินค้า ตะกร้า ฐานข้อมูล `render.yaml` `package.json` และสิ่งที่ build/server รัน
  (3) — (4) PR ที่แก้ 13.7 เอง (5) ไม่แน่ใจ · **เล็ก = ที่เหลือ** · "ใหญ่" = checker บังคับ + รายงานแยกบรรทัด · ความเข้ม = 13.5 (ข้อ (1) = ชุดเต็ม #3) · ไม่ใช่รอเจ้าของ
* **ตัดสินเล็ก/ใหญ่:** `node scripts/self-merge-check.js` บน commit หัวของ PR (checkout branch ของ PR + `git fetch origin main` · บนคอมใช้ `--pr <เลข>` ได้)
  — **รันแยกเดี่ยว ที่ commit หัวที่ตรึงไว้ แล้วค่อย merge เมื่อบรรทัดท้ายไม่ใช่ `BLOCKED`** · `SMALL` / `SITE` = เล็ก · `BIG` = ใหญ่ ·
  `BLOCKED` = ห้าม merge · รายการไฟล์ของ (1)(2) + "ไม่แตะเว็บ" = `scripts/lib/site-paths.js` ที่เดียว
* **ทาง merge:** merge commit (ไม่ squash · ไม่ข้ามด่านด้วยสิทธิ์แอดมิน) ตรึง commit หัวที่ด่านตรวจ — PR ขยับหลังตรวจ = ตรวจใหม่
* **deploy และถอยเว็บ = Friday ทำเองได้** — Render ขึ้นเว็บเองทุก merge เข้า main · build เต็ม + leak check = 13.5 #2 (ก) · Render build ล้ม = เว็บเดิมอยู่ต่อ ·
  ล้มเพราะเน็ต/ของภายนอก (เช่น ฟอนต์ Google ใน `next build`) = deploy ซ้ำ 1 ครั้ง ล้มซ้ำ = 13.3 #6 · **ถอยเว็บ** (พังวงกว้าง — พังบางหน้า = แก้เฉพาะจุด)
  = revert PR ที่ทำให้พัง แล้ว merge · เว็บล่มและรอ revert ไม่ได้ = Render → Rollback แล้วตามด้วย revert · กด Render = `docs/RECOVERY.md` ข้อ 1 / 1ก
  ผ่านเบราว์เซอร์ที่เจ้าของล็อกอินไว้แล้วเท่านั้น (Friday ไม่ใส่รหัสผ่าน · เข้าไม่ได้ = บอกเจ้าของกดข้อ 1) · ทุกครั้ง: คำอธิบาย PR (หรือ PR ที่ revert)
  จด run / commit + เว็บจริงตอบอะไร (curl) · รายงานเจ้าของ = ทำอะไร · เว็บกลับมาไหม
* **ปิดรอบ = annotated tag แล้ว push tag** (สกิล `round-close`) · ปิดรอบบนคลาวด์ = ไม่มี tag (push tag ได้ 403) ระบุจุดปิดเป็น commit แทน

### 13.8 อิสระของ Friday — 123 → 456 (กฎกลาง §12 ข้อ 20 · อ่านตามจุดประสงค์ ไม่ใช่ตามตัวอักษร)

* **123 = เป้าและทิศ** — วิธีคิดเองเต็มที่ · ทางที่ดีกว่าไปถึงเป้าเดียวกัน = ใช้เลยแล้วบอกในรายงาน · เจ้าของสั่งวิธีมาตรง ๆ = แย้ง 1 บรรทัดก่อนลงมือ
  แล้วใช้ทางที่ดีกว่า · เจ้าของบอก "ทำตามที่สั่ง" = ทำตามเป๊ะ · **456 = ทำ 123 ให้ถึงจริงแล้ว ต่อยอดเองได้เลยไม่ต้องถาม**
* **เส้นเข้ม** = ของที่ย้อนไม่ได้: เงิน/ตะกร้า · ข้อมูลลูกค้า · ข้อความห้ามขึ้นเว็บ · force push · ความลับ · ของที่ลบแล้วกู้ไม่ได้ · ข้อห้ามถาวรยังอยู่ทุกข้อ
  (กฎกลาง §8 · 13.3 · HANDOFF §17 Do not touch · คำห้าม THAI_STYLE §3 · ราคาไม่พิมพ์มือ)
* **ของที่ลูกค้าเห็นซึ่งอยู่ในเป้าของรอบ = ทำแบบถอยได้ ไม่หยุดถามก่อน** แล้วเจ้าของเคาะจากรายงานหลัง merge (แทนกฎกลาง §12 ข้อ 13 ท่อน "คนดูหรือลูกค้าเห็น")
* "อยู่ในทิศ" = ไม่ใช่ฟีเจอร์คนละเรื่อง (กฎกลาง §12 ข้อ 30) และไม่แตะ【ห้ามแตะ】ของรอบ · ต้องแตะ【ห้ามแตะ】หรือดันรอบเกิน 7 ก้อน = เสนอเป็นรอบถัดไป
* ไอเดียนอกคำสั่ง: ด่านเดียวกับงานหลัก · ลูกค้าเห็น = commit แยก + ภาพก่อน/หลัง · รายงานข้อ "ทำอะไร" ไอเดียละ 1 บรรทัด (อะไร · ถอยยังไง) · ไม่ทำให้ PR ใหญ่
* **งานต่อยอดห้ามถ่วงงานหลัก:** ต่อยอด = งานแยก ทำหลังงานหลักขึ้นเว็บ ไม่เข้าคิวก่อน · ติดหรือ checker ตีกลับ = รอไว้ งานหลักไปต่อ ·
  **ของที่พังบนเว็บจริงขึ้นก่อนเสมอ** · แก้ข้อความ = ไล่หาทุกจุดในเว็บ (ทั้ง 3 ภาษา) ให้ครบก่อนส่ง checker
* **checkpoint** ก่อนงานที่ย้อนยาก = tag / branch / merge commit ที่ชี้จุดที่ตรวจผ่านแล้ว · revert ไม่ reset
