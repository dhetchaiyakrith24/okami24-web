ต้องได้อะไร — เรียงตามความสำคัญ
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1) ตัวเลขความเร็วที่เทียบข้ามรอบได้
   - รอบ 9 วัดสองเครื่องมือ ตัวเลขเลยเทียบกันไม่ได้ (รายงานรอบ 9: PageSpeed หน้าแรก 79 · Lighthouse ในเครื่อง 6 หน้า 62–70)
   - โจทย์: ตัวเลขต้องเทียบข้ามรอบได้ · สะท้อนว่ามือถือรู้สึกเร็วขึ้นจริง · บอกว่าค่าแกว่งแค่ไหน
     เครื่องมือ ตัวชี้วัด จำนวนครั้ง การจำลองมือถือ — Code เลือกเอง แล้วเขียนเหตุผล
   - ต้องรันได้กับ production build ในเครื่อง (ก่อน/หลังแก้) และ Cowork รันซ้ำกับเว็บจริงหลัง deploy ได้ด้วยขั้นตอนเดียวกัน
   - เก็บวิธีไว้ในรีโปที่เดียว รอบหน้ารันซ้ำได้ · วัด "ก่อนแก้" ก่อนแตะโค้ด

2) เว็บเร็วขึ้นชัดบนมือถือ — ตัวงานหลัก
   - เป้า: ตัวชี้วัดในข้อ 1 ดีขึ้นชัดทุกหน้าในชุดวัด · Code ตั้งตัวเลขเป้าเองหลังวัดก่อนแก้ แล้วบอกเหตุผล
   - รอบ 9 ประเมินว่าต้นเหตุคือ JavaScript หนัก + โค้ดที่ไม่ได้ใช้ ให้ยืนยันเองก่อน ถ้าต้นเหตุอื่นหนักกว่า ไปทางนั้น
   - ภาพเคลื่อนไหว / hero / ของที่เจ้าของเคยเคาะว่าชอบ: ถ้าต้องแลกกับความเร็ว ความสวยชนะ
     ถ้าเห็นว่าแลกนิดเดียวแต่เร็วขึ้นมาก → ทำแบบถอยได้ commit แยก แนบภาพก่อน/หลัง ให้เจ้าของเคาะตอน merge
   - พิสูจน์ได้ว่าหน้าตาเหมือนเดิม (390 และ 1440) + designer

   เกณฑ์ผ่านเรื่องการใช้งาน — ต้องผ่านทุกข้อก่อน push (ของพวกนี้พึ่ง JavaScript ลดแล้วพังเงียบได้):
   - สลับภาษา (เก็บในคุกกี้ ไม่มี URL แยกภาษา): ไม่กะพริบภาษาผิด · HTML ที่ Google เห็นยังเป็นไทย
   - กล่องยืนยันอายุ (จำค่าใน localStorage): ยังขึ้นก่อนเนื้อหา · จำค่าได้ · กดได้บนจอเตี้ย
   - ตัวนับกดปุ่มไลน์: คลิกต้องไม่หายเพราะสคริปต์โหลดช้าลง
   - ค้นหา · เมนูมือถือ · ปุ่ม/ลิงก์ที่ไปไลน์ · การเปลี่ยนหน้าไม่ช้าลง
   - ตะกร้า (ปิดอยู่): พฤติกรรมและหน้าตาเหมือนเดิม — ลดโค้ดที่ใช้ร่วมกันได้ แต่ตะกร้าต้องเป็นแบบเดิม

   เกณฑ์ผ่านเรื่อง SEO:
   - เทียบ HTML ก่อน/หลังทั้งเว็บ: ลิงก์สินค้า · ข้อความหลัก · JSON-LD · canonical · meta · title ต้องเท่าเดิม (เปลี่ยนเฉพาะที่ตั้งใจ และบอกว่าอะไร)

3) หน้าเว็บหนักขึ้นเรื่อย ๆ — หาว่าโตเพราะอะไรแล้วลด
   - รายงานรอบ 9 (site-audit ทั้ง sitemap · HTML ดิบของหน้า): เฉลี่ย 85 KB (16/09) → 102 KB (23/09) · ใหญ่สุด /products ~477 KB
   - ให้วัดเองด้วยหน่วยเดียวกันทั้งก่อนและหลัง · บอกว่าโตจากรอบไหน อะไร · ลดโดยไม่ทำให้ Google เห็นเนื้อหาน้อยลง (ดูเกณฑ์ SEO ข้อ 2)

4) Googlebot ใช้แรงส่วนใหญ่ไปกับไฟล์ข้อมูลเปลี่ยนหน้า (ข้อมูลจาก Cowork · GSC Crawl stats เปิดดู 23/09 · ช่วงที่ GSC แสดงถึงวันนั้น · % ตามจำนวนคำขอ)
   - คำขอ crawl ~3.5K · ตามประเภทไฟล์: "ประเภทอื่น" 65% · JavaScript 18% · รูป 9% · HTML 7%
   - ตามวัตถุประสงค์: รีเฟรช 97% · ค้นพบ 3% · Host status ไม่มีปัญหา
   - ตัวอย่าง URL ในกลุ่ม "ประเภทอื่น" ที่ GSC แสดง (Cowork คัดมา):
     /products/coils-accessories?_rsc=14Hz9yj_Op0zMsNU · /products/pods-cartridges?_rsc=14Hz9yj_Op0zMsNU ·
     /products/disposables?_rsc=14Hz9yj_Op0zMsNU · /products/disposables?_rsc=D44D4JBgZ-l8nAH2 ·
     /privacy?_rsc=gHVZIDe6Wu2fL8bR · /brands/uwell?_rsc=… · /brands/salthub?_rsc=… · /brands/voopoo?_rsc=… · /contact?_rsc=… · /warranty?_rsc=…
   - โจทย์: ถ้า Google ไม่จำเป็นต้อง crawl ของพวกนี้ ทำให้มันเสียแรงน้อยลง แรงที่เหลือจะไปเก็บหน้าจริง
     ห้ามบล็อกของที่ Google ต้องใช้แสดงผลหน้า · ถ้าเห็นว่าไม่ควรแตะ บอกเหตุผล

5) GSC รายงาน "ตัวอย่างข้อมูลสินค้า" ถูก 12 ไม่ถูก 4 (ภาพรวม GSC 23/09 · เปิดรายละเอียดไม่ได้ อาจเป็นข้อมูลเก่า)
   - Code เปิด GSC ไม่ได้ → ตรวจ Product JSON-LD ทุกหน้าสินค้าเทียบข้อกำหนดของ Google เอง · เจอผิดแก้ · ส่งรายชื่อ URL ตัวแทนมาให้ Cowork รัน Rich Results Test บนเว็บจริงหลัง deploy
   - ราคาใน JSON-LD ต้องดึงจาก catalog เท่านั้น ห้ามพิมพ์มือ
