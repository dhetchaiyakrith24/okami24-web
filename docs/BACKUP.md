## เก็บไว้ที่ไหน

- **ในเครื่องนี้:** โฟลเดอร์ `C:\Users\dhetc\OKami24-backups\` (นอกโปรเจกต์ นอก git)
- **บนโฮสต์ (Render สิงคโปร์ ตั้งแต่ 2026-09-06):** `/var/data/backups` บนดิสก์ถาวรก้อนเดียวกับฐานข้อมูล — ตั้งด้วยตัวแปร `OKAMI24_BACKUP_DIR` ใน `render.yaml` · ถ้าลืมตั้ง ระบบจะใช้ `<OKAMI24_DATA_DIR>/backups` ให้เอง เพื่อไม่ให้สำเนาไปนอนในโฟลเดอร์ชั่วคราวที่หายตอน deploy ใหม่
- ไฟล์ชื่อ `okami24-2026-09-06T21-05-33.db` (วัน-เวลาที่สำรอง) · ไฟล์ .env อยู่ใน `env\<วัน-เวลา>\`
- `latest.json` = สรุปรอบล่าสุด · `backup.log` = ประวัติทุกรอบ 1 บรรทัดต่อรอบ
- เก็บ **60 ชุดล่าสุด** ชุดเก่ากว่านั้นถูกลบอัตโนมัติ (ลบเฉพาะไฟล์ที่ระบบนี้สร้างเอง)
- **ห้ามแนบไฟล์สำรองในรายงานหรือส่งให้ใคร** — มีข้อมูลลูกค้า

## ทำงานอัตโนมัติยังไง

- ทุกครั้งที่เซิร์ฟเวอร์เว็บเปิด (ทั้ง `next dev` และ `next start`) จะสำรองครั้งแรกหลัง 15 วินาที แล้วสำรองซ้ำ**ทุก 6 ชั่วโมง** ตราบที่เซิร์ฟเวอร์ยังเปิดอยู่ (ไม่ต้องตั้ง Task Scheduler ของ Windows — ไม่ได้แตะการตั้งค่าเครื่อง)
- ทุกรอบตรวจสำเนาทันที (SQLite `integrity_check` + นับออเดอร์) ถ้าสำเนาเสียจะลบทิ้งและบันทึกว่าล้ม ไม่ทับของดี
- ปิดได้ด้วย `OKAMI24_BACKUP_DISABLED=1` · เปลี่ยนความถี่ด้วย `OKAMI24_BACKUP_INTERVAL_MINUTES` (ค่าเริ่มต้น 360)
- สำรองไม่สำเร็จ = ขึ้น `[backup] ... FAILED` ใน log ของเซิร์ฟเวอร์ เว็บยังทำงานต่อตามปกติ

เห็นบรรทัด `OK    C:\Users\dhetc\OKami24-backups\okami24-....db` = สำเร็จ

## ทดสอบว่ากู้คืนได้จริง (ไม่แตะฐานข้อมูลจริง)

```bash
npm run backup:restore-test
```
สคริปต์จะคัดลอกสำเนาล่าสุดไปไว้ใน `_incoming\restore-test\<วัน-เวลา>\` (โฟลเดอร์แยก) เปิดอ่าน ตรวจความสมบูรณ์ นับแถวทุกตาราง แล้วเทียบกับฐานข้อมูลจริง · เห็น `PASS` = กู้ได้ · มี `report.json` ในโฟลเดอร์นั้น

> **`PASS` แปลว่าอะไร (และไม่ได้แปลว่าอะไร) — เจ้าของยืนยัน 2026-09-06 ตามผู้ตรวจภายนอก**
> `PASS` = เปิดไฟล์สำรองได้ โครงสร้างครบ อ่านตารางได้ · **ไม่ได้แปลว่ากู้ทั้งระบบกลับมาใช้งานได้ และสำเนายังอยู่ที่เดียวกับฐานข้อมูล** — ดิสก์พังทั้งก้อน = หายทั้งคู่ · บนโฮสต์มี snapshot รายวันของ Render ช่วยอีกชั้น · **สำเนาออกนอกโฮสต์ยังเป็นงานค้าง**

## กู้คืนจริง (เมื่อฐานข้อมูลหาย/พัง) — ทำทีละขั้น

> ขั้นตอนข้างล่างเขียนสำหรับ**เครื่องนี้** · ถ้าเป็นเว็บที่ออนไลน์อยู่บน Render ให้บอก Javis ทำให้ (ไฟล์อยู่บนดิสก์ `/var/data` เข้าถึงผ่านหน้า Shell ของ Render) **อย่าแก้เองบนโฮสต์**

1. **ปิดเซิร์ฟเวอร์เว็บก่อน** (กด Ctrl+C ในหน้าต่างที่รัน `next start` / `next dev`)
2. เปิดโฟลเดอร์ `C:\Users\dhetc\OKami24-backups\` เลือกไฟล์ `okami24-<วัน-เวลา>.db` ที่ใหม่ที่สุด (หรือรอบก่อนหน้าถ้ารอบล่าสุดคือตอนที่ข้อมูลพังแล้ว)
3. ในโฟลเดอร์โปรเจกต์ `.data\` — ถ้ามีไฟล์ `okami24.db`, `okami24.db-wal`, `okami24.db-shm` อยู่ ให้**ย้ายทั้ง 3 ไฟล์ออกไปเก็บ**ที่อื่นก่อน (อย่าลบ)
4. คัดลอกไฟล์สำรองที่เลือกมาวางใน `.data\` แล้วเปลี่ยนชื่อเป็น `okami24.db`
5. เปิดเซิร์ฟเวอร์ใหม่ → เปิดหน้า `/orders/<เลขออเดอร์>` ที่รู้ว่ามี ถ้าเห็น = กู้สำเร็จ
6. ถ้ามีไฟล์ `.env*` หาย ให้คัดลอกจาก `OKami24-backups\env\<วัน-เวลา>\` กลับมาวางที่รากโปรเจกต์

## สิ่งที่ยังไม่ครอบคลุม (ตามความจริง)

- สำเนาอยู่**บนดิสก์ก้อนเดียวกับฐานข้อมูล** — กันไฟล์เสีย/ลบผิดได้ แต่ไม่กันดิสก์พังทั้งก้อน · บนโฮสต์ Render ถ่าย snapshot ของดิสก์ให้ทุกวันเป็นชั้นที่สอง · **สำเนาออกนอกโฮสต์ไปเลย (ดิสก์ภายนอก/คลาวด์ส่วนตัว) ยังเป็นงานค้าง** — ห้ามใช้ GitHub เก็บ
- เซิร์ฟเวอร์ปิดอยู่ = ไม่สำรอง (แต่ก็ไม่มีออเดอร์ใหม่เข้า)
- รูปสินค้าและโค้ดอยู่ใน git อยู่แล้ว ไม่รวมในระบบนี้
