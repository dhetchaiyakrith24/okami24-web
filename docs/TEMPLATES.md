## (ก) แม่แบบไฟล์คำสั่งรอบ — 7 หัวข้อ เรียงตามนี้เสมอ · ≤200 บรรทัด

```
<ชื่อรอบ> — ฉบับ <n> · เขียน <วันที่>
main = <commit 7 ตัว> (PR #<n> live) · git fetch ก่อนเริ่ม · <ห้ามแตะเว็บ / แตะได้เฉพาะ …>

【รอบนี้ทำเพื่ออะไร】
 <เจ้าของสั่งอะไร วันไหน — 1-3 บรรทัด · เกณฑ์ผ่านของทั้งรอบ 1 บรรทัด>

【ห้ามแตะ】
 · <ไฟล์/โฟลเดอร์/ระบบที่ห้ามแตะรอบนี้ — นอกเหนือจาก HANDOFF §17 "Do not touch" ซึ่งใช้ทุกรอบ>
 · <ของที่เจ้าของตัดสินแล้ว ห้ามถามซ้ำ (กฎกลาง §12 ข้อ 17)>

【แตะได้】<เฉพาะรอบที่ต้องแก้ไฟล์ล็อก (รายการ = 13.7 "ตัวล็อก") — เขียนชื่อไฟล์บนบรรทัดนี้ ไม่มี = ลบหัวข้อนี้>

【ก้อน 1】<ชื่อก้อน> — ชั้น A (ข้อความล้วน) / ชั้น B (แตะโครง)
 ผลที่ต้องเป็นจริงเมื่อจบก้อน: <1-5 บรรทัด — เขียนผลลัพธ์ ไม่ใช่ขั้นตอน (ค)-1 · วิธีทำและ agent ที่ใช้ = Friday เลือกเอง (13.2)>
 รู้ได้ยังไงว่าเสร็จ: <เกณฑ์วัดได้>
【ก้อน 2】…
【ก้อน n】… (ไม่เกิน 7 ก้อน — 13.8)

【ตรวจ】
 · <เฉพาะด่านที่เพิ่มจากมาตรฐาน — มาตรฐาน = 13.5 (ชุดเบา/ชุดเต็ม) · ไม่มี = เว้นหัวข้อนี้>

【ส่งมอบ】
 · push ลง branch งานได้ทุกเมื่อ (13.7) · merge หลัง checker ผ่าน (13.7) · อัปเดต §16 ตอนปิดก้อน/ย้ายแชท (13.6)
 · ปิดรอบ = สกิล `round-close` ขั้น 5 (คอม = tag <ชื่ออังกฤษ> + push tag · คลาวด์ = commit ปิดรอบ ไม่มี tag) · รายงานตาม (ข)

【ถ้าติด】
 · <กรณีที่ให้หยุดถาม — นอกเหนือจาก 13.3 ซึ่งใช้ทุกรอบ>
 · <ไฟล์คำสั่งไม่ต้องวางแผน context ให้ Code — Code วัดเองแล้วย้ายแชทตามสกิล `okami24-handoff` (ค)–(จ)>
```

หมายเหตุการใช้: หัวข้อไหนไม่มีของ ลบหัวข้อทิ้งได้ · คำสั่ง = เป้า + เกณฑ์ผ่าน + ของห้ามแตะ ไม่เขียนวิธีทำ (13.8 "123 = ทิศทาง ไม่ใช่ขั้นตอน") · ข้อความที่ลูกค้าจะเห็น = Friday เลือกแบบถอยได้ เจ้าของเคาะเก็บ/ถอยจากรายงานหลัง merge (13.3 ย่อหน้าท้าย · 13.8) · ถ้ารอบต้องแบ่งหลายแชท ใส่ "แชท A / แชท B" ไว้ใต้【รอบนี้ทำเพื่ออะไร】พร้อมบอกว่าแชทไหนจบที่ขั้นไหน

## (ข) แม่แบบรายงาน — ตามกฎกลาง §12 ข้อ 10 (รูปแบบ = ที่นั่นที่เดียว) · ส่วนของเว็บ = 13.6

```
<บรรทัดแรก = เสร็จหรือยัง งานอะไร>
แก้อะไรไป       — <ทีละข้อ ภาษาคน · หน้าเว็บที่เปลี่ยน = ลิงก์เว็บจริง + ชื่อสินค้า · ทำเพิ่มเอง (13.8) = บอกว่าเพิ่มเอง + ถอยยังไง>
ติดปัญหา        — <ปัญหาที่เจอ + แก้แล้วหรือยัง · จุดที่เบี่ยงจากคำสั่งหรือตัดสินเอง + เหตุผล · ไม่มี = ไม่ใส่>
ตรวจ            — <1 บรรทัด ใครตรวจ ผลเป็นยังไง (ป้าย [ตรวจแล้ว] ฯลฯ ตามกฎกลาง §12 ข้อ 9) · เล่าละเอียดเฉพาะตรวจไม่ผ่านหรือตรวจไม่ได้ · หลักฐาน = ลิงก์>
ต้องตัดสินใจ/ทำ   — <คำถามตอบคำเดียว (ใช่/ไม่ หรือ 1/2/3 · A/B/C) + คำแนะนำ · สิ่งที่เจ้าของต้องทำเอง · ไม่มี = "ไม่มี">
งานค้าง         — <เขียนเป็นคำ>
ใช้เวลา          — <รวมกี่นาที (ผู้ตรวจกี่นาที) · เสียเวลาผิดปกติตรงไหน ถ้ามี>
```
สิ่งที่ห้ามใส่ในประโยค = กฎกลาง §12 ข้อ 10 · ของเทคนิคอยู่ในคำอธิบาย PR หรือไฟล์ที่ลิงก์ (13.6)

**ความยาวและที่อยู่ของรายละเอียด = กฎกลาง §12 ข้อ 10** · ของนอกรายการ (ทำเองนอกคำสั่ง 456 ตาม 13.8) = หัวข้อ "แก้อะไรไป" ไอเดียละ 1 บรรทัด (อะไร · ถอยยังไง) + ภาพก่อน/หลังถ้าลูกค้าเห็น — สกิล `round-close` ขั้น 7 ชี้มาที่นี่

รวม/ลบกฎ = diff ของ commit คือบันทึก ไม่ต้องกางข้อความเต็มแยกไฟล์ (เจ้าของ 28/09)

## (ค) กติกาเขียนคำสั่งให้ Code — 8 ข้อ **[เจ้าของเคาะ 2026-09-22]**

> **หมวดนี้ผูกพันคนเขียนคำสั่ง (Cowork/เจ้าของ) ไม่ใช่กฎที่ Code ต้องทำตาม** — เขียนไว้ตรงนี้เพื่อให้ Code อ่านได้เอง และใช้เป็นเกณฑ์ตอนตรวจคำสั่ง (สกิล `round-open` ขั้น 3)
> ที่มา: รอบ backlink ปิด 2026-09-22 — เจ้าของถาม Code ทุกรอบว่าคำสั่งตรงไหนบอกวิธีเกินจำเป็น แล้วเอาคำตอบ 4 รอบมาเขียนเป็นกติกา
> **ทุกข้อที่มีกฎอยู่แล้วในรีโป = ชี้ไป ไม่เขียนซ้ำ** (คำตัดสินถาวร = HANDOFF §18)

1. **เขียน "ต้องได้อะไร" ไม่ใช่ "ทำยังไง"** — ทุกก้อนขึ้นต้นด้วยผลที่ต้องเป็นจริงเมื่อจบก้อน (ช่องในแม่แบบ (ก) บังคับรูปแบบนี้แล้ว) · เกณฑ์ "รู้ได้ยังไงว่าเสร็จ" = กฎกลาง §12 ข้อ 12
2. **แยกข้อห้ามออกจากวิธีทำ** — 【ห้ามแตะ】กับข้อเท็จจริง เขียนให้แน่นเท่าที่รู้จริง · ส่วนวิธีทำปล่อยหลวม (Code เลือกทางเองตามกฎกลาง §12 ข้อ 15 และเถียงกลับได้ตามข้อ 16)
3. **ใส่ตัวเลขที่วัดได้วันนี้ พร้อมบอกว่าวัดด้วยอะไร** — เช่น "ลิงก์สินค้า→บทความ = 0 จาก 61 หน้า (นับจาก `<main>` ของทุก URL ใน sitemap)" Code จะได้ตั้งด่านบนตัวเลขเดียวกันแล้ววัดก่อน/หลังได้ · **Code วัดใหม่เองเสมอ ไม่ใช้เลขในไฟล์คำสั่งเป็นด่าน** (`round-open` ขั้น 2 · `scope-auditor`) — เลขในไฟล์คำสั่งคือจุดตั้งต้น ไม่ใช่หลักฐาน
4. **ใส่ท่อน "ทิศทางของรอบ" ทุกรอบ** — เขียนบรรทัดเดียวว่า "ทิศทางของรอบนี้คือ …" แล้วชี้ไป 13.8 (สิทธิ์ทำไอเดียนอกคำสั่ง — หลัก 1-2-3 → 4-5-6 = ไฟล์กลาง หมวด 12 ข้อ 20) · ห้ามลอกข้อความสิทธิ์มาใหม่ ทิศทางคือของใหม่รอบเดียว สิทธิ์ไม่ใช่ · ทิศทางนี้คือสิ่งที่ #1 ใช้วัดว่าไอเดีย "อยู่ในเป้าของรอบ" ไหม
5. **ห้ามท่องกฎที่มีอยู่แล้วในรีโป** — ชี้ที่อยู่ของกฎแทน (13.x · HANDOFF §17 · สกิล) · ใช้กับไฟล์คำสั่งรอบเท่านั้น — บรีฟที่ส่งให้ agent ยังต้องกางกฎที่ agent นั้นต้องใช้ เพราะ agent เริ่มโดยไม่มี context (`catalog-research` SKILL.md)
6. **ไม่วางจุดหยุดก่อน merge** — Friday merge แล้วรายงาน (13.7 · เจ้าของ 01/10 · 14/10) · ยกเว้น PR อ่านสต็อกรายเช้า = เจ้าของยืนยันในแชทก่อน merge
7. **เพิ่มงานกลางรอบ = แก้รายการ【ห้ามแตะ】/ไฟล์ที่อนุญาตในข้อความเดียวกัน** — ถ้าไม่แก้ Code ถือว่าขอบเขตเดิมยังอยู่ แล้วหยุดถามตาม 13.3 (เคสจริง: รอบ SEO ข ไฟล์คำสั่งห้ามแตะ `seo.ts`/`src/app` แล้วสั่งงานที่ต้องแตะไฟล์นั้นกลางแชท) · **ข้อนี้ไม่ได้เปิดทางให้พ่วงฟีเจอร์ — กฎกลาง §12 ข้อ 30 "หนึ่งรอบหนึ่งเรื่อง ห้ามพ่วง" ยังอยู่เหมือนเดิม** ข้อนี้พูดถึงกรณีที่งานที่สั่งเพิ่มอยู่ในทิศทางเดิมของรอบอยู่แล้ว แต่ไปชนรายการไฟล์ที่ไฟล์คำสั่งเขียนห้ามไว้ตอนต้นรอบ · ถ้าเป็นฟีเจอร์คนละเรื่อง = รอบใหม่ ไม่ใช่แก้รายการไฟล์
8. **ตอนปิดรอบ ถาม Code ว่าคำสั่งตรงไหนบอกวิธีเกินจำเป็นหรือขวางทางที่ดีกว่า** — คำตอบอยู่ในหัวข้อ "ติดปัญหา" ของรายงาน (`round-close` ขั้น 7) · คำตอบที่ได้มาเข้าหมวดนี้ในรอบถัดไป
